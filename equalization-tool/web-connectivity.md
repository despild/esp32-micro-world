# ESP32 로컬 웹과 QR 접속 설계

2026-11-11. ESP32가 Wi-Fi 접속점과 웹서버를 제공하고, 휴대폰에서 실시간 그래프를 보는 방안입니다. 현재 [WebQrTest](firmware/WebQrTest/README.md)를 보드에 올려 AP·QR 프레임버퍼·내부 HTTP 응답과 Android Chrome의 실제 웹 접속을 검증했습니다. 휴대폰 카메라의 작은 OLED QR 인식, 센서 취득·그래프·CSV·무선 ON/OFF 메뉴는 구현 전 또는 미검증입니다. BMP180과 포트형 센서는 향후 같은 웹 화면을 사용하도록 설계합니다.

테스트 펌웨어는 부팅하면 AP를 켜고, 현재 압력 대신 연결 상태와 OLED 확인 버튼을 제공합니다. 아래 필요할 때만 켜는 방식은 완성품의 설계안입니다.

## 접속 흐름

1. 기기의 설정에서 `폰 연결`을 켜면 ESP32 SoftAP를 시작합니다. 평소 독립 측정에서는 Wi-Fi를 끕니다.
2. 휴대폰으로 Wi-Fi 접속 QR을 읽고 기기 네트워크에 연결합니다. QR이 읽히지 않으면 OLED에 표시한 SSID/암호로 직접 연결합니다.
3. 연결 안내 페이지가 자동으로 나타나면 진입합니다. 나타나지 않으면 브라우저에서 `http://192.168.4.1`을 엽니다. 이 주소는 펌웨어에서 고정하도록 제안합니다.
4. 현재 압력·그래프·피크·기록·CSV 내보내기를 로컬 웹에서 제공합니다. 폰 화면은 기록 중 열어 두며, 화면 잠금·백그라운드 전환 중 연속 수신을 보장하지 않습니다.

HTML/CSS/JavaScript를 ESP32에 함께 저장해 인터넷, 클라우드 서버, 앱 설치 없이 기본 기능이 동작하게 합니다. 외부 CDN·폰트·로그인은 초기안에 넣지 않습니다. iPhone과 Android의 일반 브라우저로 접속하는 방식이므로 Web Bluetooth 지원에 의존하지 않습니다.

Espressif는 ESP32-C3용 HTTP/WebSocket 기능과 SoftAP captive portal 예제를 제공합니다. 포털 예제는 DNS/HTTP 리디렉션 또는 DHCP 정보를 사용합니다. 자동 열림과 다운로드 동작은 휴대폰별 검증이 필요하며, 수동 IP 접속 경로를 유지합니다. [공식 HTTP 서버 문서](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-reference/protocols/esp_http_server.html), [공식 포털 예제](https://github.com/espressif/esp-idf/tree/master/examples/protocols/http_server/captive_portal)

인터넷 없는 Wi-Fi라는 휴대폰 안내가 나와도 기기 연결을 유지해야 합니다. 장시간 그래프와 CSV 저장은 포털의 작은 창보다 일반 브라우저에서 확인하도록 안내하고 실제 기종으로 검증합니다.

### 실제 Android Chrome 접속 문제와 해결

실물 시험에서 Wi-Fi는 연결됐지만 Chrome에서 `ERR_TOO_MANY_RETRIES`가 발생했고 `/api/status`도 열리지 않았습니다. 사용자가 **Chrome의 로컬 네트워크 권한을 허용하자 해결**됐습니다. 이후 보드에서 클라이언트 1대와 초당 웹 요청 증가를 확인했습니다. HTTP 오류 해결 원인은 사용자 확인에 따른 것으로, Wi-Fi 검색 문제까지 같은 원인으로 단정하지 않습니다.

같은 증상이면 Android 설정 → 앱 → Chrome → 권한에서 **근처 기기/로컬 네트워크** 항목이 있는지 확인합니다. OS·앱 버전에 따라 표시와 적용 대상이 다릅니다. Android 공식 문서는 Android 17을 대상으로 하는 앱의 로컬 통신 권한을 설명하며, 이 권한은 `NEARBY_DEVICES` 그룹에 속합니다. 이 기기 자체의 `http://192.168.4.1` 접속과 공개 웹사이트에서 사설망으로 요청하는 브라우저 정책은 구분합니다. [Android 공식 로컬 네트워크 권한](https://developer.android.com/privacy-and-security/local-network-permission)

## Wi-Fi QR과 URL QR의 차이

| QR 종류 | 담는 정보 | 동작 |
|---|---|---|
| Wi-Fi 접속용 | SSID, 인증 방식, 암호 | 휴대폰이 기기 Wi-Fi에 연결하도록 안내 |
| 웹 주소용 | `http://192.168.4.1` | 기기 Wi-Fi에 이미 연결된 상태에서 웹 화면 열기 |

Wi-Fi QR 하나가 모든 휴대폰에서 네트워크 연결과 웹 화면 열기를 모두 처리한다고 가정하지 않습니다. 1차안은 **Wi-Fi QR → 포털 또는 직접 IP 접속**이며, 필요하면 버튼으로 웹 주소 QR 화면을 따로 보여줍니다. Wi-Fi QR의 `WIFI:T:WPA;S:...;P:...;;` 형식은 [ZXing 문서](https://github.com/zxing/zxing/wiki/Barcode-Contents#wi-fi-network-config-android-ios-11)를 참고합니다. 암호는 기기별로 설정하며 QR에 담긴 값과 실제 AP 설정을 일치시킵니다.

## 현재 72×40 OLED의 한계

표준 QR Version 1은 21×21 모듈이고 사방에 4모듈 여백이 필요하므로 총 29×29 칸입니다. 한 모듈을 2×2픽셀로 그리면 최소 58×58픽셀이어서 높이 40픽셀인 현재 화면에는 들어가지 않습니다. [DENSO QR 크기](https://www.qrcode.com/en/about/version.html), [필수 여백](https://www.qrcode.com/en/howto/code.html)

한 모듈당 1픽셀로 그리면 Version 1~3의 전체 크기는 각각 29, 33, 37픽셀로 수치상 들어갑니다. Version 4는 여백 포함 41픽셀로 맞지 않습니다. 필요한 버전은 문자열 길이·문자 종류·오류 복원 수준에 따라 달라집니다. SSID와 암호가 있는 QR은 짧은 URL보다 더 커질 수 있습니다.

이는 **그릴 수 있는 크기 계산이지 카메라 인식 검증이 아닙니다.** 0.42인치 화면에서는 실제 QR이 매우 작습니다. 밝은 배경에 어두운 모듈과 필수 여백을 확보하고, 화면 덮개·반사·밝기·거리·휴대폰 초점을 포함해 시험해야 합니다. 여백을 잘라내거나 비정수 배율로 찌그러뜨리지 않습니다.

비용을 줄이는 1차안은 기존 OLED에 SSID/암호/IP를 순환 표시하고, 케이스에 충분히 크게 인쇄한 Wi-Fi QR 스티커를 붙이는 것입니다. 화면 QR은 스캔 시험을 통과할 때 추가합니다. 더 큰 128×64 OLED도 Version 1의 2배 표시는 가능하지만 Version 2는 여백 포함 높이 66픽셀이므로 모든 Wi-Fi QR을 2배로 표시할 수 있다고 가정하지 않습니다.

## 전력과 안정성

- 무선 모듈 추가 비용은 없습니다. Wi-Fi가 켜진 사용시간은 독립 측정과 따로 실측하고, 기본은 필요할 때만 켜는 방식으로 설계합니다.
- 초기 웹 모드는 BLE 동시 사용을 제외하고 폰 1대 연결부터 검증합니다. BLE는 별도 선택 모드/후속 기능으로 유지합니다.
- 센서 취득을 일정 주기로 수행하고 WebSocket에는 여러 샘플을 묶어 보냅니다. BMP180 시제품은 25–50 Hz 취득 목표, 웹 전송은 10–20회/초부터 시험합니다.
- 시각화 지연이나 느린 수신 때문에 센서 읽기를 멈추지 않도록 버퍼 크기를 제한하고, 누락은 순번·시간·상태로 표시합니다. 재연결 시 무손실 복원을 보장하지 않습니다.
- 웹과 OLED 모두 같은 영점·범위·오류 상태를 사용합니다. 영점 조정은 압력 입력을 대기에 개방한 뒤 사용자가 실행합니다.
- 모바일 브라우저의 CSV 다운로드, 화면 잠금, 연결 복귀, 인터넷 없는 Wi-Fi 유지, Wi-Fi 송신 중 저전압 재부팅 여부를 실제 폰과 배터리로 검증합니다.

앱 개발·배포 비용을 줄이려면 로컬 웹을 먼저 구현할 가치가 있습니다. 배터리 사용시간은 무선 방식 이름만으로 정하지 않고 완성 회로의 평균·순간 전류를 비교합니다.
